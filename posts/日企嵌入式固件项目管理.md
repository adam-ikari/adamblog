# 日企嵌入式固件项目管理 —— 给非技术背景的人

## 这到底是什么项目？

想象一个没有屏幕、没有键盘的小电脑，藏在空调遥控器、洗衣机面板、汽车刹车系统里。它通电就自己跑，坏了只能拆机修。这个"小电脑里的程序"就是**固件**。

固件项目管理和普通软件开发最大的区别：

- **和硬件绑在一起**：软件做完了，还要等硬件造出来才能测
- **改起来代价大**：不像 App 点一下更新，固件升级通常需要专用工具
- **出错后果严重**：一个 bug 可能让整批产品召回

所以日企做这类项目，管理极度严谨。

---

## 核心术语速查

| 术语 | 含义 |
|------|------|
| 発注（はっちゅう） | 客户向供应商下订单，正式委托开发 |
| 人月（にんげつ） | 一个人干一个月的工作量，计价基本单位 |
| システム設計 | 系统设计（基本設計），画架构、定模块 |
| 詳細設計 | 细化到每个函数、每个接口 |
| 実装（じっそう） | 编码实现 |
| 生産性（せいさんせい） | 每人月产出多少代码量 |
| 千行当たり不具合 | 每千行代码的缺陷数，衡量质量 |

---

## 项目从哪开始：発注

日企固件项目通常不是自己团队说干就干，而是**客户発注 → 供应商受注**。

- 客户发 RFQ（Request for Quotation），附上要件概要
- 供应商根据要件估算人月，报价
- 双方合意后，正式発注，项目启动

発注阶段决定了项目的**范围、工期、金额**，后面改什么都得走变更流程。

---

## 算账的基本单位：人月

人月是日企固件项目最核心的计量单位。

### 典型的人月分配

| 阶段 | 占比 |
|------|------|
| システム設計 | 10~15% |
| 詳細設計 | 15~20% |
| 実装（编码） | 25~30% |
| テスト | 35~45% |
| 出荷・保守対応 | 5~10% |

测试占大头，这是固件项目的特征——硬件不可逆，测不充分就出货，后果是批量召回。

### 人月单价

日企固件开发的人月单价因公司层级不同：

- 元请（直接对接客户）：150~250 万円/人月
- 一次下请：100~150 万円/人月
- 二次下请：60~100 万円/人月

每往下分包一层，单价砍一刀，但管理成本也转移一层。

## 設計阶段：システム設計 → 詳細設計

### システム設計（基本設計）

**做什么**：定架构，不写代码。

- 系统构成图（模块划分）
- 状态迁移图（设备状态机）
- メモリマップ（ROM/RAM 分配）
- タスク構成（RTOS 任务优先级）

**产出物**：基本設計書，客户评审签字才能往下走。

### 詳細設計

**做什么**：把基本设计拆到函数级。

- 每个函数的入参、返回值、例外处理
- 数据结构定义
- 接口时序图

**日企特点**：詳細設計書的详细程度，经常让外企的人觉得"这都能当代码读了"。但正是这种细度，让后面的実装和テスト成本大幅降低。

## 実装（编码）与生産性

### 実装工程

- 按照コーディング規約（MISRA-C / 公司规约）编写
- 静态分析工具（PC-Lint / QAC）跑一遍
- コードレビュー（Code Review），逐行审查

### 生産性指标

日企常用**生産性**来衡量团队效率：

| 指标 | 典型值 | 说明 |
|------|--------|------|
| 実装生産性 | 300~500 步/人月 | 一个人一个月写 300~500 行代码 |
| ドキュメント生産性 | 50~100 頁/人月 | 设计书、测试报告等 |
| テスト生産性 | 100~200 テストケース/人月 | 测试用例编写和执行 |

**注意**：这里说的"步"（step）通常指正味の実装行数，不含空行和注释。C 语言固件项目 300~500 步/人月是行业平均水平，汽车电子等要求高的领域会更低。

## 质量管理：千行不具合

**千行当たりの不具合**（缺陷密度）是日企最看重的质量指标之一。

### 目标值

| 工程阶段 | 目标值 | 含义 |
|----------|--------|------|
| 単体試験後 | ≤ 5.0 件/千行 | 单元测试后，每千行代码不超过 5 个 bug |
| 結合試験後 | ≤ 1.0 件/千行 | 集成测试后降到 1 个以下 |
| 総合試験後 | ≤ 0.2 件/千行 | 系统测试后几乎清零 |
| 出荷後 | 0 件/千行 | 出货后不允许有 bug |

### 管理上的用法

- 每个阶段结束后，统计**発見不具合数 ÷ 総ステップ数 × 1000**
- 如果实际值远超目标，说明前一个工程没做到位，需要**手戻り**（返工）
- 出荷前不具合残数必须为 0，否则客户不検収

### 典型的不具合分布

| 原因 | 占比 |
|------|------|
| 仕様理解不足 | 30~40% |
| 設計ミス | 25~35% |
| コーディングミス | 15~20% |
| テスト漏れ | 10~15% |
| その他 | 5~10% |

有趣的是，大部分 bug 的根源不在编码，而在**需求没搞清楚**和**设计有漏洞**。这也是日企为什么在設計レビュー上花那么多时间。

## PM 的日常

### 四个核心会议

| 会议 | 频率 | 内容 |
|------|------|------|
| 朝会 | 每天 | 昨天干了什么、今天干什么、卡在哪 |
| 進捗会議 | 每周 | 进度 vs 计划、风险、课题 |
| 不具合トリアージ | 每周 | bug 优先级、谁修、啥时候改完 |
| レビュー会 | 按里程碑 | 设计书评审、代码评审 |

### 三个核心工具

1. **スケジュール表**（甘特图）：谁、什么时候、干什么
2. **課題管理表**：待解决的问题，谁负责、啥时候解决
3. **不具合管理表**：所有 bug 的追踪状态

## 常见的管理坑

| 坑 | 表现 | 对策 |
|----|------|------|
| 文档太多 | 写三个月设计书，编码时间不够 | 核心详细、次要精简 |
| 需求变来变去 | 客户加功能但不加工期 | 走正式变更流程，先评估再报价 |
| 外包失控 | 下请团队进度不透明 | 设里程碑验收点，定期成果物レビュー |
| HW/SW 不同步 | 硬件改版了软件不知道 | 建立 HW/SW 合同レビュー机制 |
| 缺测试资源 | 2 块板子 5 个人排队用 | 启动时就规划好硬件数量 |
| 生产性虚高 | 代码行数灌水，但功能没多少 | 用"機能ポイント/人月"替代"步/人月" |
| 千行不具合好看但实际质量差 | 测试用例太少，bug 没测出来 | 規定テストカバレッジ目標 |

---

## 一句话总结

> 日企固件项目管理 = **発注で範囲を決め、人月で見積り、設計書で品質を作り込み、千行不具合で管理する**。本质是用流程的严谨性覆盖硬件不可逆的风险。
