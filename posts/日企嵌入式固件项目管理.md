# 国内日企嵌入式固件项目管理 —— 给非技术背景的人

## 这到底是什么项目？

想象一个没有屏幕、没有键盘的小电脑，藏在空调遥控器、洗衣机面板、汽车刹车系统里。它通电就自己跑，坏了只能拆机修。这个"小电脑里的程序"就是**固件**。

固件项目管理和普通软件开发最大的区别：

- **和硬件绑在一起**：软件做完了，还要等硬件造出来才能测
- **改起来代价大**：不像 App 点一下更新，固件升级通常需要专用工具
- **出错后果严重**：一个 bug 可能让整批产品召回

所以国内日企（日资在中国设立的研发中心/分公司）做这类项目，管理风格继承了日本总部的严谨，但落地在中国本土，形成了独特的工作方式。

---

## 国内日企的工作氛围

**几个基本事实：**

- **会议讲中文**，但术语全用日语——没人说"进度会议"，都说"進捗会議"
- **文档中英日混排**：正文写中文，标题用日语，代码注释用英文
- **汇报对象是日本人**：周报月报要翻译成日语，或者至少用日语术语
- **团队里可能有日本出向者**（从日本总部派来的驻在员），平时用中日混合语交流
- **客户可能是日本总部**，也可能是中国本地客户，管理风格有差异

## 项目从哪开始：発注（hacchuu）

国内日企的固件项目通常不是自己想干就干，而是**客户発注（hacchuu）→ 受注**。

- 客户可能是日本总部，也可能是国内客户
- 发 RFQ（询价书），附上要件定義（youken teigi）概要
- 供应商根据要件估算人月（ningetsu），做見積り（mitsumori，报价）
- 报价单位通常是**人民币**，但内部核算时还会换算成日元给日本总部看
- 双方合意后，正式発注，项目启动

発注阶段决定了项目的**范围、工期、金额**，后面改什么都得走变更流程——国内日企的变更流程和日本总部一样严格，但沟通成本更高（因为要中日文翻译）。

---

## 算账的基本单位：人月（ningetsu）

人月（ningetsu）是核心计量单位。一个人干一个月 = 1 人月。

### 典型的人月分配

| 阶段 | 日语 | 占比 |
|------|------|------|
| 系统设计 | システム設計（shisutemu sekkei） | 10~15% |
| 详细设计 | 詳細設計（shousai sekkei） | 15~20% |
| 编码 | 実装（jissou） | 25~30% |
| 测试 | テスト（tesuto） | 35~45% |
| 出货维护 | 出荷・保守対応 | 5~10% |

测试占大头，这是固件项目的特征——硬件不可逆，测不充分就出货，后果是批量召回。

---

## 設計阶段：システム設計 → 詳細設計

### システム設計（系统设计 / 基本設計）

**做什么**：定架构，不写代码。

- 系统构成图（模块划分）
- 状态迁移图（设备状态机）
- メモリマップ（memori mappu，内存分配表）
- タスク構成（tasuku kousei，RTOS 任务优先级）

**产出物**：基本設計書（kihon sekkeisho），客户评审签字才能往下走。

在国内日企，设计书通常**中文写正文，标题用日语**，关键术语保留日语原文。这样中国员工写得快，日本客户也能看懂。

### 詳細設計（详细设计）

**做什么**：把基本设计拆到函数级。

- 每个函数的入参、返回值、例外处理
- 数据结构定义
- 接口时序图

**国内日企特点**：詳細設計書的详细程度，和中国本土互联网公司完全不是一个量级。但正是这种细度，让后面的実装和テスト成本大幅降低——这也是国内日企能长期稳定交付高质量固件的原因。

## 実装（jissou，编码）与生産性（seisansei）

### 実装工程

- 按照コーディング規約（koudingu kiyaku，编码规范）编写，规范通常继承日本总部，少数会本地化
- 静态分析工具（PC-Lint / QAC）跑一遍
- コードレビュー（kōdo rebyū），逐行审查——国内日企的 Code Review 通常用中文交流，但注释写日语或英文

### 生産性（seisansei）指标

国内日企常用**生産性**来衡量团队效率：

| 指标 | 日语 | 典型值 | 说明 |
|------|------|--------|------|
| 编码生产率 | 実装生産性（jissou seisansei） | 10~20 步/小时 | 一个人一小时写 10~20 行代码 |
| 文档生产率 | ドキュメント生産性（dokyumento seisansei） | 2~4 页/小时 | 设计书、测试报告等 |
| 测试生产率 | テスト生産性（tesuto seisansei） | 4~8 用例/小时 | 测试用例编写和执行 |

**注意**：这里说的"步"（step）通常指正味の実装行数，不含空行和注释。C 语言固件项目 10~20 步/小时是行业平均水平，汽车电子等要求高的领域会更低。

## 质量管理：千行当たり不具合（sengyou atari fuguai）

**千行当たりの不具合**（缺陷密度）是国内日企最看重的质量指标之一。计算公式：

> 千行不具合 = 発見不具合数（hakken fuguaisuu）÷ 総ステップ数（sou steppusuu，总代码行数）× 1000

### 目标值

| 工程阶段 | 日语 | 目标值 | 含义 |
|----------|------|--------|------|
| 单元测试后 | 単体試験後（tanshi shiken go） | ≤ 5.0 件/千行 | 每千行代码不超过 5 个 bug |
| 集成测试后 | 結合試験後（ketsugou shiken go） | ≤ 1.0 件/千行 | 降到 1 个以下 |
| 系统测试后 | 総合試験後（sougou shiken go） | ≤ 0.2 件/千行 | 几乎清零 |
| 出货后 | 出荷後（shukka go） | 0 件/千行 | 不允许有 bug |

### 管理上的用法

- 每个阶段结束后，统计千行不具合
- 如果实际值远超目标，说明前一个工程没做到位，需要返工
- 出货前不具合残数（fuguai zansuu，剩余缺陷数）必须为 0，否则客户不検収（kenshuu）

### 典型的不具合分布

| 原因 | 日语 | 占比 |
|------|------|------|
| 需求理解不足 | 仕様理解不足（shiyou rikai fusoku） | 30~40% |
| 设计错误 | 設計ミス（sekkei misu） | 25~35% |
| 编码错误 | コーディングミス（koudingu misu） | 15~20% |
| 测试遗漏 | テスト漏れ（tesuto more） | 10~15% |
| 其他 | その他（sono ta） | 5~10% |

有趣的是，大部分 bug 的根源不在编码，而在**需求没搞清楚**和**设计有漏洞**。这也是国内日企为什么在設計レビュー上花那么多时间。

## PM 的日常

### 四个核心会议

| 会议 | 国内日企叫法 | 频率 | 内容 |
|------|-------------|------|------|
| 晨会 | 朝会（choukai） | 每天 15 分钟 | 中文交流，但说"昨日の実績""今日の予定" |
| 进度会议 | 進捗会議（shinchoku kaigi） | 每周 | 进度 vs 计划，风险、课题，中日双语 |
| Bug 优先级会 | 不具合トリアージ（fuguai toriaaji） | 每周 | bug 优先级、谁修、啥时候改完 |
| 评审会 | レビュー会（rebyuukai） | 按里程碑 | 设计书评审、代码评审，中文为主 |

### 三个核心工具

| 工具 | 国内日企叫法 | 用途 |
|------|-------------|------|
| 甘特图 | スケジュール表（sukejuuru hyou） | 谁、什么时候、干什么 |
| 课题管理表 | 課題管理表（kadai kanri hyou） | 待解决的问题，谁负责、啥时候解决 |
| Bug 追踪表 | 不具合管理表（fuguai kanri hyou） | 所有 bug 的追踪状态 |

国内日企的 Excel 模板通常直接继承日本总部，表头全是日语，但填的内容是中文。

## PMO 的工作

在国内日企，PM 和 PMO 是两回事。PM 管"做什么、多少钱、什么时候交"，PMO 管"怎么管"。

### PMO 的主要职责

| 职责 | 日语 | 说明 |
|------|------|------|
| 进度管理 | 進捗管理（shinchoku kanri） | 每周更新进度表，标注遅延（延迟）和課題（问题） |
| 课题管理 | 課題管理（kadai kanri） | 所有未解决的问题登记在案，跟踪到关闭 |
| 风险管理 | リスク管理（risuku kanri） | 提前识别风险，制定対策（对策） |
| 品质管理 | 品質管理（hinshitsu kanri） | 不具合管理、レビュー実施状況追踪 |
| 会议运营 | 会議運営（kaigi un'ei） | 議事録（会议纪要）作成、指摘事項跟踪 |
| 报告制作 | 報告書作成（houkokusho sakusei） | 向日本总部汇报的月报、周报——需要中日双语 |

### PMO 的日常产出物

- **週報（shuuhou）**：每周进度报告，含実績 vs 計画、課題一覧——中文写内容，标题用日语，关键数据加日语注释方便日本总部看
- **月報（geppou）**：月度汇总，含品質指標（千行不具合等）、リスク状況
- **議事録（gijiroku）**：每次正式会议的纪要，记录決定事項（决定事项）和宿題（待办事项）

## 注意：日企中的"検討"不是"检讨"

中文读者容易误解的一个词：**検討（kentou）**。

在国内日企，検討的意思是**讨论、研究、审议**，和中文字面的"检讨"（自我批评）完全不是一回事。

常见用法：

| 用法 | 国内日企的实际含义 |
|------|-------------------|
| 仕様を検討する | 讨论规格方案，通常开検討会 |
| 設計検討会 | 设计评审会，不是"设计检讨会" |
| 課題を検討する | 研究问题解决方案 |
| 前向きに検討する | 积极考虑——日企经典暧昧表达，实际上可能只是"知道了，没承诺" |

**注意最后一个**：「前向きに検討します」在国内日企也经常听到。字面意思是"会积极讨论"，但作为乙方，听到这句话要追问具体 schedule，否则可能不了了之。

## 常见的管理坑

| 坑 | 表现 | 对策 |
|----|------|------|
| 文档太多 | 写三个月设计书，编码时间不够 | 核心详细、次要精简 |
| 需求变来变去 | 客户加功能但不加工期 | 走正式变更流程，先评估再报价 |
| HW/SW 不同步 | 硬件改版了软件不知道 | 建立 HW/SW 联调机制，定期对齐版本 |
| 缺测试资源 | 2 块板子 5 个人排队用 | 启动时就规划好硬件数量，提前采购 |
| 日文沟通障碍 | 中国员工不懂日语术语，理解偏差 | 新人入职时做术语培训，文档加中文注释 |
| 生产性虚高 | 代码行数灌水，但功能没多少 | 用"機能ポイント/人月"替代"步/小时" |
| 千行不具合好看但实际质量差 | 测试用例太少，bug 没测出来 | 規定テストカバレッジ目標 |

---

## 一句话总结

> 国内日企固件项目管理 = **発注で範囲を決め、人月で見積り、設計書で品質を作り込み、千行不具合で管理する**。中文沟通、日语术语、中日双语汇报，本质是用流程的严谨性覆盖硬件不可逆的风险。
